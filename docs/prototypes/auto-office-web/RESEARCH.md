# Auto Office Web UI reconnaissance

Research date: 2026-10-03. Inspected source ref: `745add02c7b4afbad67c04e0a06712c1def15084`. Re-read current HEAD before implementation. This research supports [the Web UI map](https://github.com/Hikari9/auto-office/issues/276); it does not ratify a UI, host topology or operator action policy.

## Runtime findings

1. **Observe the runtime; do not build another lifecycle.** The [database module](https://github.com/Hikari9/auto-office/blob/745add02c7b4afbad67c04e0a06712c1def15084/src/office/db.py) makes `runs.db` transactional authority, with tasks, dispatches, revisions, gates, events, per-consumer cursors, outbox and session bindings. The schema already carries run/dispatch Office versions, role, harness/model/effort, process and pane identities, timestamps, task PR JSON and landing metadata. Use these records as evidence, not terminal text as lifecycle truth.
2. **`office status` is not a safe dashboard polling endpoint.** [guide.status](https://github.com/Hikari9/auto-office/blob/745add02c7b4afbad67c04e0a06712c1def15084/src/office/guide.py) reads orchestrator events and advances the `orchestrator` cursor in a transaction. Browser polling must have an independent cursor/read-only projection. Also, `db.connect()` creates directories, sets WAL and invokes migrations; do not present it as a side-effect-free observer connection. A proposed observer must avoid migrations and lifecycle writes, fail clearly on unsupported schema, and not use SQLite immutable mode against an actively changing database.
3. **Alive, busy, accepted and unavailable are different.** [rerun.agent_alive / agent_activity](https://github.com/Hikari9/auto-office/blob/745add02c7b4afbad67c04e0a06712c1def15084/src/office/rerun.py) distinguish Herdr lookup from PID-based headless liveness and return unknown when observation fails. Headless liveness is not reliable proof of productive progress. Show observed activity with its own timestamp, and explicit paused, quota-wait, ingestion-pending, unavailable, exited and disconnected states. Do not fabricate percent progress, token use or cost from elapsed time. Task acceptance counts are not time estimates.
4. **Orchestrator chat needs a new, explicit attachment contract.** [prompting.prompt](https://github.com/Hikari9/auto-office/blob/745add02c7b4afbad67c04e0a06712c1def15084/src/office/prompting.py) resolves a task or dispatch, requires a live Herdr pane and distinguishes landed, held and unconfirmed sends. That is not a general browser-to-caller-orchestrator endpoint. Add a proven orchestrator session binding and capability handshake; do not infer ownership from the most recently active pane or forward browser text to arbitrary shell commands. Worker/reviewer messaging remains forbidden in this UI even where the CLI technically supports it. The proposed command receipt needs durable idempotency and queued/delivered/unknown/failed semantics. Unknown delivery must not be blindly retried.
5. **Transcript support is evidence-specific, not universal streaming.** [transcripts.py](https://github.com/Hikari9/auto-office/blob/745add02c7b4afbad67c04e0a06712c1def15084/src/office/transcripts.py) reads Claude/Codex session logs and validates prompt-marker, cwd and start-time relationships for dispatch replies. Reuse these identity protections. An incremental, bounded, redacted browser activity feed is additional work. Unsupported harnesses should show unavailable evidence rather than borrowed transcripts. Returned text must be escaped; links and rendered Markdown need a safe policy.
6. **Preserve current release-line semantics.** [frontdoor.py](https://github.com/Hikari9/auto-office/blob/745add02c7b4afbad67c04e0a06712c1def15084/src/office/frontdoor.py) selects the newest installed PATCH on the run's MAJOR.MINOR line; cross-line upgrade is explicit. This supersedes older exact-version prose. Display the run's recorded version plus the actual serving runtime when known; never treat the UI version as either one. Historical evidence must retain its own identity.

Reported issues such as [reviewer reply ingestion delay](https://github.com/Hikari9/auto-office/issues/275), [idle worker after rejected submit](https://github.com/Hikari9/auto-office/issues/259), and [orphan dispatches after reboot](https://github.com/Hikari9/auto-office/issues/257) motivate visible uncertainty and attention reasons. They were read as reports, not reproduced in this research. Do not conflate a frontend with fixes to those runtime defects.

## GitHub findings

Context7 was consulted against `/websites/github_en_rest`, then the official documentation below was checked directly.

- [Authenticated-user repository listing](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user) covers explicit owner, collaborator and organization-member access, subject to the credential's actual permissions. [Installation repository listing](https://docs.github.com/en/rest/apps/installations#list-repositories-accessible-to-the-app-installation) covers the app installation, not every repository that the human can access. A local `gh` credential is a candidate for local-first use; an app/user authorization model is a candidate for hosted use. Neither choice is ratified. Show credential scope honestly and paginate; public-user listings are not an adequate replacement for the requested private-access repository switcher.
- [Issue endpoints](https://docs.github.com/en/rest/issues/issues#list-repository-issues) may include pull requests. Separate them using the returned pull-request discriminator rather than counting every item as an issue. Preserve repository IDs and issue/PR identities rather than keying by number alone. A visible repository is not necessarily attached to an Office checkout, writable, unarchived or issue-enabled.
- [GitHub API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) recommend webhooks where feasible, conditional requests for efficient polling, pagination, rate-limit handling and careful mutation pacing. Proposed local-first fallback: server-side cache, coalesced lazy fetches, ETags and backoff. Do not independently poll GitHub from every row or browser tab. Use separate freshness for GitHub data and local runtime observations; a network failure retains a labeled stale snapshot, but revoked access removes restricted cached content.
- Model issue-to-run and run/task-to-PR associations as many-to-many with provenance. Explicit recorded links outrank inference. A branch-name guess or textual mention is not authoritative membership. PR draft/ready, base/head, current revision, checks/reviews, mergeability, Office gates and user authority remain separate fields. Native issue hierarchy/blocking should be consumed as actual relationships, not regex-matched task lists. The current schema's lack of a dedicated normalized GitHub association table means the exact migration/API seam still belongs in implementation design; do not assume arbitrary goal text is a reliable join key.

## Proposed integration shape - not a ratified decision

An optional host-side adapter exposes read models and tightly scoped commands. The browser holds disposable view state, not runtime authority. The host uses established Office operations for writes and server-side GitHub credentials. A static desktop frontend can be served by the companion without forcing a permanent daemon on existing CLI users. This is smaller than inventing a hosted control plane before remote/multi-host requirements are chosen.

Key identities: host ID, GitHub repository ID, canonical checkout ID, run ID, role/session ID, task ID, revision ID, PR ID and independent event cursor. Selecting a different repo/run must never silently retarget a draft. A host registration must advertise readback and orchestrator-message capability separately; unsupported caller sessions remain inspect-only with a clear explanation.

A proposed update model is snapshot plus incremental events with cursor replay. [Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) support event IDs and reconnect; a separately authenticated HTTP command path is sufficient for text messages. SSE is a transport candidate, not proof of exactly-once delivery. Define server retention and reset behavior; reconcile a snapshot after cursor expiration. Bound activity buffers, subscribe to detailed output only for the selected agent, pause unnecessary work when hidden, and preserve focus/scroll during incremental updates.

For a local-first choice: bind loopback by default, validate Host/Origin, protect commands against CSRF and unexpected browser origins, never expose tokens to frontend storage, and reject cross-host/run targets. A remote or multi-host choice requires an explicit authenticated transport and stronger account/host scoping, not merely binding the listener to every interface.

## Implementation verification frontier

Test a read-only snapshot/event subscription leaves lifecycle state and the orchestrator cursor unchanged; missing/old schema does not trigger observer migrations; liveness unknown never displays active progress; historical runs cannot inherit current evidence; role spoofing cannot enable worker messages; commands validate current binding and authority; repeated/lost-response messages do not duplicate delivery; revoked GitHub permission clears cached restricted content; stacked PR checks are tied to the right revision. Reuse current fake-harness tests and add browser interaction tests.

Proposed, unmeasured scale fixture: 100 visible repositories, 10,000 indexed issues, 50 active dispatches; bounded/virtualized rows and log buffers. Set measurable targets at ratification rather than claiming this 12-issue mockup meets production budgets. No charts are required in v1: issue/run/task relationships and exceptions carry the useful information.

Remaining human decisions: select A/B/C or a named hybrid, choose local versus remote/multi-host scope, define lifecycle actions beyond orchestrator chat, then ratify acceptance. The prototype and recommendations do not decide these on the maintainer's behalf.
